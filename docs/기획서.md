# 마지막 불꽃 (Last Spark) — 상세 기획서

> The 10% Battery Lounge
> 폰이 꺼지기 전, 가장 뜨겁게 타오르는 10분

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 서비스명 | 마지막 불꽃 (영문: Last Spark / 부제: The 10% Battery Lounge) |
| 슬로건 | 폰이 꺼지기 전, 가장 뜨겁게 타오르는 10분 (Burn bright before your phone dies) |
| 컨셉 | 배터리 잔량 10% 이하 상태에서만 입장 가능한, 국가별로 매칭되는 2D(패럴랙스 배경 + 도트 캐릭터, 데이브 더 다이브 스타일) 메타버스 시한부 라운지 |
| 플랫폼 | iOS / Android (React Native + Expo, 크로스플랫폼) |
| 주요 타겟 | 전 세계 심야 스마트폰 과몰입 유저(Doomscrollers), Z세대, 2030 직장인·학생 |
| 지원 언어 | 한국어(KR), 영어(EN), 일본어(JA), 스페인어(ES) |

### 1.1 핵심 컨셉과 재미 요소

이 서비스의 핵심 재미는 "제약이 만드는 희소성"이다. 배터리가 10% 이하로 떨어져야만 입장할 수 있다는 조건은 유저가 평소 회피하려는 상태(방전 직전)를 오히려 기다리게 만드는 역설적 동기를 만든다. 여기에 다음 세 가지 장치가 몰입을 강화한다.

- **시한부성**: 방전이라는 물리적 한계가 정해진 세션 종료 시점을 만들어, 대화와 관계 형성에 절박함과 밀도를 부여한다.
- **동시성 압박**: 전 세계에서 지금 이 순간 배터리가 다 되어가는 사람들만 모인다는 설정이 "지금 여기 있는 사람들"에 대한 동질감을 만든다.
- **의식(ritual)화**: 유언, 묘비, 방전 제단 같은 장치가 단순 채팅을 넘어 하나의 작은 의식처럼 느껴지게 하고, 이것이 SNS 공유로 이어지는 바이럴 포인트가 된다.

## 2. 핵심 시스템 아키텍처

### 2.1 캐릭터 생성 및 에셋 운영 방식

- 실시간 이미지 AI 생성은 배제하고, 사전 제작된 10~20종의 2D 도트 스프라이트 시트를 클라이언트에 내장한다.
- 라운지 입장 시 무작위(Random Gacha)로 캐릭터 1종을 즉시 할당하여 대기 시간 0초(Instant Join)를 달성한다.
- 닉네임은 기기 설정 언어 기반 익명 템플릿(예: "배터리 4% 남은 고양이", "야근 3일차 직장인")을 기본 부여하고 유저가 직접 수정할 수 있다.

#### 2.1.1 아트 디렉션 — 2D 패럴랙스 배경 + 도트 캐릭터 (데이브 더 다이브 스타일)

정교하게 그려진 2D 배경 위에 도트(픽셀 아트) 캐릭터를 얹는 방식을 채택한다. 실시간 3D 렌더링은 쓰지 않는다 — 배경은 고정 시점의 이미지 한 장, 또는 원경·중경·근경 2~3개 레이어로 나눠 패럴랙스 스크롤 효과를 주는 형태로 구성한다. 데이브 더 다이브가 참고 지점이다 — 손그림 느낌의 컬러감 있는 2D 배경과 단순화된 픽셀 캐릭터를 자연스럽게 매칭시킨 스타일.

- **배경**: Higgsfield로 생성한 고해상도 2D 일러스트. 실시간 3D 씬 조립이 필요 없어 "이미지 생성 결과물이 곧 완성 배경"에 가깝다.
- **캐릭터**: 도트 스프라이트를 배경 위에 2D 레이어로 얹는다. 배경의 톤(채도·명도)에 캐릭터 팔레트를 맞춰야 붕 떠 보이지 않는다 — 이 톤 매칭이 이 조합에서 가장 신경 써야 할 부분이다.
- **시점/카메라**: 고정 시점(탑다운에 가까운 구도). 자유 회전이나 3D 카메라 이동은 없고, 캐릭터가 화면 안에서 좌우/상하로 이동하는 정도다.
- **난이도**: 실시간 3D(HD-2D) 렌더링 방식 대비 엔지니어링 비용이 크게 낮다 — 3D 엔진, 카메라 컨트롤, 포스트프로세싱 셰이더가 전부 불필요해지고 `react-native-skia` 같은 표준 2D 렌더링 스택으로 충분하다(9장 참고). 디자이너 없이 솔로로 진행하기에 훨씬 현실적인 선택이다.

### 2.2 전체 상태 머신 (State Machine)

| 상태 | 진입 조건 | 주요 동작 | 전이 |
|---|---|---|---|
| **A. 대기 모드** | 앱 진입 시 기본 상태(배터리 잔량 무관) | 내 캐릭터 표시, 입장 가능 여부 안내, 자국 묘비 갤러리·명예의 전당 열람, 상단 전광판 롤링, 10% 도달 푸시 알림 예약 | 배터리 ≤10% & 미충전 상태에서 유저가 '입장'을 누르면 → B |
| **B. 라운지 진입** | 배터리 ≤10% AND 미충전 AND 유저의 입장 확인 | 기기 Locale/IP 기반 국가별 라운지로 자동 매칭(3장 참고), 룸당 정원 30명(초과 시 국가 내 N호점 자동 생성) | 충전 감지 → C / 배터리 1% → D 진입 가능 / 배터리 0% → E |
| **C. 비상 카운트다운** | 라운지 체류 중 충전기 연결 | 전체 비상 사이렌·붉은 조명, 배신자 머리 위 10초 타이머 | 10초 내 분리 → 생존모션 후 B 복귀 / 10초 경과 → 낙뢰 이펙트, 강제 퇴장(세션 종료) |
| **D. 1% 임종 모드** | 배터리 1% | 중앙 '방전 제단' 접근 권한 활성화, 전체 공지 배너 유언 송출(최대 30자), 보상형 광고 시청 시 3분 유예 | 방전 유예 성공 → B 복귀 / 0% 도달 → E |
| **E. 방전/사망 처리** | 배터리 0% 또는 앱 종료 | 퇴장 위치에 도트 묘비 생성, 유언장 DB 영구 기록 | → A 복귀 |

## 3. 라운지 테마 명세

시차(Timezone)와 언어 장벽을 차단하기 위해 룸 매칭 자체는 국가/지역별로 계속 분리한다(기기 Locale/IP 기준). 다만 비주얼 테마는 국가마다 다르게 만들지 않고 하나로 통일한다 — 즉 KR 룸도, US 룸도, JP 룸도 전부 같은 "사이버펑크 폐허 바" 모습이고, 서로 다른 국가의 유저는 다른 룸 인스턴스에 배정될 뿐 같은 배경을 보게 된다. 이렇게 하면 언어 장벽 문제(룸 분리)는 그대로 해결하면서, 배경 에셋 제작량은 국가별로 다른 테마를 만들 때보다 1/N로 줄어든다(9.4 참고).

### 3.1 출시 버전 (V1) — 국가별 룸 매칭 + 단일 통일 테마

| 항목 | 내용 |
|---|---|
| 공간 테마 (전 국가 공통) | 사이버펑크 폐허 바 |
| 대표 에셋 | 네온 칵테일, CRT 모니터 |
| 환경음(BGM) | 글리치 전자음, 빗소리 |

- **룸 매칭**: 기기 Locale/IP로 국가 코드를 판별해 같은 국가 유저끼리 룸을 공유한다(예: KR, US, JP 등). 사용자 수가 적은 국가는 "글로벌(GL)" 공용 버킷으로 묶는다.
- **수용 인원**: 룸당 최대 30명 제한, 정원 초과 시 해당 국가 룸 내에서 2호점·3호점 자동 생성
- **여권 시스템**: 타 국가 라운지 수동 방문은 V1에서는 보류(어차피 테마가 동일해 방문 유인이 적음). V2에서 국가별 테마가 생기면 함께 도입한다.

### 3.2 향후 업데이트 후보 (V2+) — 국가별 테마 분리

반응이 좋으면 룸 매칭은 그대로 두고 국가별로 서로 다른 비주얼 테마를 적용하는 것을 고려한다. 초기 기획 당시 준비했던 3개국 테마 초안을 그대로 남겨둔다.

| 항목 | 한국 (KR) | 북미 (US) | 일본 (JP) |
|---|---|---|---|
| 공간 테마 | 심야 주황 천막 포장마차 | 80s 심야 네온 다이너 | 붉은 홍등 골목 이자카야 |
| 대표 에셋 | 초록 소주병, 뚝배기, 플라스틱 의자 | 머그잔, 버거, 주크박스 | 사케 도쿠리, 생맥주 잔 |
| 환경음(BGM) | 쇠젓가락 부딪힘, 찌개 끓는 소리 | 커피 따르는 소리, LP 노이즈 | 잔 챙챙 소리, 풍경 종소리 |

## 4. 화면별 상세 인터랙션 명세

### 4.1 대기 화면 (앱 진입 시 기본 화면)

배터리 잔량과 무관하게 앱을 켜면 항상 이 화면부터 시작한다. 라운지 입장은 되돌릴 수 없는 시한부 세션의 시작이므로, 조건을 만족해도 자동으로 넘어가지 않고 유저가 직접 입장을 확인한다.

- **내 캐릭터**: 화면 중앙에 이번 세션의 캐릭터와 닉네임 표시(라운지에 그대로 입장한다)
- **입장 상태 안내**: 배터리 > 10% 또는 충전 중이면 '대기 중', 배터리 ≤10% & 미충전이면 '입장 가능' + 입장 버튼
- **실시간 배터리 트래커**: 현재 배터리 잔량 수치 표기, "입장까지 N% 남음" 안내
- **명예의 묘비 갤러리**: 자국 유저들이 전날 밤 남긴 유언장 목록(좋아요 정렬)
- **입장 예약 푸시 알림**: 배터리 10% 도달 즉시 로컬 푸시 발송
- **상단 전광판**: '명예의 전당 전광판' 아이템 구매 유저의 유언을 24시간 고정 롤링 노출

### 4.2 메인 라운지 화면 (배터리 ≤10%, 미충전)

**A) 배터리 잔량별 시각/물리 효과**

| 구간 | 상태 | 시각 효과 | 이동 속도 |
|---|---|---|---|
| 10~6% | 안정기 | 정상 도트 렌더링, 기본 조명 | 100% |
| 5~3% | 주의기 | 땀방울 스프라이트, 조명 30% 감쇄, 비네팅 | 80% |
| 2~1% | 임종기 | 50% 반투명화(유령화), 붉은 경고등 점멸, 글리치 쉐이더 | 55~60% |

**B) 소통 및 인터랙션**

- **근접 텍스트 채팅**: 캐릭터 기준 반경 150px 이내 유저에게만 말풍선 표시
- **비언어 도트 리액션**: 감정 버튼(해골·배터리·잔·묘비) 클릭 시 머리 위 3초간 애니메이션
- **시한부 건배**: 상대 캐릭터 터치 시 햅틱 진동 + 잔 부딪히는 효과음

**C) 중앙 방전 제단 (1% 전용)**

- 배터리 잔량 1% 유저만 제단 영역 진입 가능
- 텍스트 입력(최대 30자) 시 라운지 상단 전체 긴급 속보 배너로 송출
- 0% 도달 또는 연결 종료 시 해당 좌표에 묘비 에셋 생성, 유언장 아카이브 테이블에 영구 저장

**D) 충전기 연결 시 10초 비상 시퀀스**

1. 0초 — 충전 감지 즉시 라운지 전체 붉은 비상등 전환, 사이렌 사운드, 배신자 머리 위 10초 타이머 생성
2. 1~9초(분리 성공) — 비상 해제, 캐릭터 3초간 무릎 꿇고 헐떡이는 모션 후 정상 복귀, 시스템 메시지 송출
3. 10초(처형) — 낙뢰 이펙트, 캐릭터 폭발 후 앱 대기 화면으로 세션 강제 종료, 시스템 메시지 송출

## 5. 데이터베이스 스키마 및 네트워크 프로토콜

### 5.1 Database Schema (PostgreSQL / Supabase)

**묘비 및 유언장 아카이브 테이블 (`gravestones`)**

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | UUID (PK, default gen_random_uuid()) | 고유 ID |
| country_code | VARCHAR(5) | 국가 코드 |
| nickname | VARCHAR(30) | 작성자 닉네임 |
| last_words | VARCHAR(100) | 유언 텍스트 |
| skin_id | VARCHAR(20) | 사망 당시 도트 스킨 ID |
| grave_type | VARCHAR(20) | 묘비 종류(basic / gold / neon) |
| likes_count | INT (default 0) | 공감/좋아요 수 |
| created_at | TIMESTAMP WITH TIME ZONE | 생성 일시 |

**사용자 인벤토리 테이블 (`user_inventory`)**

| 컬럼 | 타입 | 설명 |
|---|---|---|
| user_id | UUID (PK) | 유저 ID |
| has_traitor_pass | BOOLEAN | 배신자 프리패스 보유 여부 |
| equipped_grave | VARCHAR(20) | 장착 중인 묘비 스킨 ID |

### 5.2 Socket.io 실시간 이벤트 명세

| 이벤트 | 방향 | 페이로드 | 설명 |
|---|---|---|---|
| `lounge:join` | C→S | `{countryCode, batteryLevel, charId, nickname}` | 국가/지역 라운지 룸 입장 요청(countryCode로 룸 매칭, 정원 30명 초과 시 같은 국가 내에서 분점 배정) |
| `lounge:joined` | S→C | `{roomId, countryCode, capacity, occupants}` | 입장 요청에 대한 서버 확인 응답(룸 배정 결과) |
| `player:sync_move` | C→S | `{x, y, direction}` | 2D 좌표 이동 상태 동기화 |
| `player:sync_move` | S→C | `{x, y, direction, playerId}` | 같은 룸의 다른 플레이어 이동 브로드캐스트 |
| `battery:change` | C→S | `{batteryLevel}` | 배터리 1% 감소 시 서버 전달, 상태 연출 갱신 |
| `presence:update` | S→C | `{roomId, occupants}` | 룸 인원 변동(입장/퇴장) 동기화 |
| `emergency:detach` | C→S | (없음) | 충전기 분리(생존) 신호 |
| `emergency:start` | S→C | `{playerId, timer:10}` | 충전 감지 알림, 10초 카운트다운/사이렌 발동 |
| `emergency:cancel` | S→C | `{playerId}` | 10초 내 분리 성공, 정상 상태 복귀 |
| `traitor:execute` | S→C | `{playerId}` | 10초 초과 시 낙뢰 처형 연출 브로드캐스트, 강제 퇴장 |
| `altar:submit` | C→S | `{message}` | 1% 제단 유언 작성 요청(서버가 길이·상태 검증) |
| `altar:broadcast` | S→C | `{nickname, message}` | 검증된 유언을 라운지 전체 배너로 송출 |

C→S 요청과 그 결과를 알리는 S→C 이벤트는 서로 다른 이벤트로 분리한다(`altar:submit`→`altar:broadcast`, `emergency:detach`→`emergency:cancel`). 클라이언트가 보낸 값을 서버가 검증한 뒤 뿌려야 하기 때문이다.

## 8. 리스크 및 고려 사항

프로덕션 전환 전 반드시 검토가 필요한 지점들이다.

- **플랫폼 배터리 API 제약**: iOS Safari/WebKit 기반 웹뷰는 Battery Status API를 지원하지 않는다. 네이티브 앱에서도 iOS는 `UIDevice.batteryLevel`을 통해 앱이 포그라운드일 때만 값을 읽을 수 있어, "배터리 10% 도달 시 즉시 푸시"는 백그라운드 폴링 주기와 OS의 배터리 절약 정책에 의해 정확도가 떨어질 수 있다. Android도 제조사별 백그라운드 프로세스 제한(도즈 모드 등)을 고려해야 한다.
- **부정 사용 가능성**: 에뮬레이터나 배터리 값 조작 툴로 실제 배터리 상태를 위조해 상시 라운지에 머무는 어뷰징 시나리오가 존재한다. 서버 측에서 짧은 시간 내 비정상적인 배터리 변화 패턴을 감지하는 최소한의 검증 로직이 필요하다.
- **스토어 심사 리스크**: "충전을 방해/지연하도록 유도하는 UX"(비상 카운트다운, 처형 연출)가 일부 스토어 심사 기준에서 사용자 안전 관련 지적을 받을 가능성이 있다. 실제 충전 자체를 막는 것이 아니라 게임 내 캐릭터 페널티임을 UX 문구로 명확히 해야 한다.
- **디지털 웰빙 이슈**: 배터리 방전을 기다리게 만드는 게임 설계는 스마트폰 과사용을 정당화·심화시킬 수 있다는 비판을 받을 수 있다. 앱 내 "오늘의 방전 횟수" 같은 은근한 사용량 노출, 또는 과도한 재접속을 유도하지 않는 쿨다운 장치를 함께 고려할 필요가 있다.
- **국가/IP 기반 매칭의 정확도**: VPN 사용자나 여행객의 경우 IP 기반 국가 매칭이 실제 위치와 다를 수 있다. V1은 여권 시스템(수동 선택)이 없으므로 매칭이 틀리면 사용자가 스스로 룸을 바꿀 방법이 없다는 점을 감안해, 기본 매칭 로직에 최소한의 오차 허용(예: 애매하면 GL 버킷으로 폴백)을 넣어두는 것이 좋다.
- **실시간 서버 확장성**: 국가별로 룸을 나누면 각국 심야 시간대 피크가 자연스럽게 분산되는 효과가 있지만, 그래도 특정 국가(예: 한국) 내에서 동시 접속이 몰리는 순간은 발생한다. Redis Adapter 기반 다중 인스턴스 구조를 초기 설계 단계부터 반영해야 한다.

### 9.4 디자인·에셋 파이프라인 (전속 디자이너 없이 진행)

전속 디자이너를 두지 않는다는 전제 하에, 이 프로젝트에서 실질적으로 체감 품질을 가장 크게 좌우하는 것이 에셋(배경·캐릭터·소품)이라는 점을 고려해 배경과 캐릭터의 제작 방식을 다르게 가져간다. 2D 패럴랙스 배경 방식이므로 Higgsfield의 이미지 생성 결과물이 곧 완성 배경에 가깝고, 별도의 3D 씬 조립 같은 엔지니어링 단계가 필요 없다는 점이 가장 큰 특징이다.

| 구분 | 확정 도구 | 비고 |
|---|---|---|
| 아트 디렉션 고정 | (도구 아님) 색상 팔레트(5~6색), 조명 톤, 레퍼런스 2~3장을 가장 먼저 확정 | 이 기준 없이 생성을 시작하면 결과물마다 톤이 달라져 나중에 전부 다시 만들어야 한다 |
| 배경 일러스트(V1 사이버펑크 폐허 바 1종) | **Higgsfield** (generate_image, 패럴랙스 사용 시 원경/중경/근경 레이어로 나눠 생성 → 부족한 영역은 outpaint_image로 확장) | 완성된 배경 이미지를 직접 얻는 단계. 3D 씬 조립 같은 후속 엔지니어링 작업이 없다 |
| 캐릭터 도트 스프라이트 + 애니메이션 | **PixelLab** | 픽셀 그리드·워크사이클 등 캐릭터 애니메이션에 특화되어 있어 이 용도에는 Higgsfield보다 적합 |
| 환경음·효과음(BGM, 사이렌, 건배음 등) | **Higgsfield** (generate_audio) | 별도 사운드 도구 없이 동일 서비스에서 커버 가능 |
| 마케팅 숏폼 영상(7장 바이럴 전략) | **Higgsfield** (generate_video, shorts 관련 워크플로우) | 배경/캐릭터 에셋과 같은 도구로 이어서 제작 가능 |
| 배경-캐릭터 합성 검수 | (도구 아님) 배경 위에 도트 캐릭터를 실제로 얹어 스케일·톤 확인(2.1.1 참고) | 이 단계를 건너뛰면 배경과 캐릭터가 서로 다른 게임처럼 보이는 문제가 가장 흔하게 발생한다 |

| 커스텀 폰트/타이포그래피 | 별도 필요 — 무료 픽셀 폰트(예: 구글 폰트의 도트 계열) 검색해 사용 | Higgsfield·PixelLab 둘 다 폰트 제작 도구는 아님 |
| UI 화면 레이아웃 | Figma(코드/의도 기반 생성 가능) | 디자이너 없이도 화면 구조 정리에 활용 가능 |
| 번역 관리 | Lokalise 또는 Crowdin | KR/EN/JA/ES 문자열 관리 |

**도구 조합 평가**

캐릭터·배경·사운드·마케팅 영상 전부 Higgsfield와 PixelLab 두 도구로 대부분 커버된다. 배경은 Higgsfield의 이미지 생성 결과물을 거의 그대로 완성 배경으로 쓸 수 있어, 별도의 3D 씬 조립·엔지니어링 단계가 없다는 점이 HD-2D(실시간 3D) 방식 대비 가장 큰 장점이다. 다만 스프라이트 시트 패킹, 커스텀 폰트, 캐릭터 10~20종의 톤을 배경과 통일하는 일관성 관리는 별도로 챙겨야 한다.

**AI 생성 에셋 사용 시 주의점**
- 라이선스: 상업적 이용 가능 여부를 생성 도구/에셋팩별로 확인한다. CC0 표기 에셋은 안전하고, AI 생성물은 서비스 약관상 상업적 사용 허용 범위를 확인해야 한다.
- 일관성: 프롬프트나 레퍼런스를 고정하지 않으면 캐릭터 10~20종의 톤이 서로 어긋나기 쉽다. 하나를 기준 삼아 나머지를 그 위에서 파생시키는 방식을 권장한다.
- 반응이 좋으면 그때 특정 에셋(예: 대표 캐릭터, 키 비주얼)만 선별적으로 전문가에게 리터치를 맡기는 것도 현실적인 절충안이다.
